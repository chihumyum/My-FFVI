# Source battle forced return

The common battle VM decodes all ten exact zero-operand `BattleForceExit` sites as `force-return`. The wrapper advances to the original following instruction immediately. `WEB_BATTLE_EVENT_CONTROLS` is required before constructing a battle that contains this request. The existing source flag contract admits only its independently implemented flag14/19 declarations; unknown flags and nonordinary judgment modes gain no new admission.

`BattleGame` owns the request and the distinct `forced` terminal phase. Enabled judgment gives this request priority over ordinary win, defeat and retreat, including an unresolved staged action. Pending and staged work stays suspended until the whole battle owner is retired. This is separate from `RemoveAllAct`, whose six source sites use the independently implemented executor cancellation lifecycle.

Forced=4 does not execute native `SaveParameter`, `SaveRecoveryCondition`, victory results or escape entry. It awards no experience, Gil, learning, loot, defeat registrations or escape count. The new owned return envelope contains participant identities and borrowed history; it cannot carry mutable HP, MP, rows, equipment, conditions or inventory. `GameState.prepareForcedReturn` validates the exact lease/history and records one `forced` receipt while preserving the entry owned state. A forced receipt does not count as a won encounter or learning receipt.

`GameSession.prepareBattleReturn` joins that owned transaction with the existing staged shared-event return and field continuation. `GameBattleHandoff`, Flow and Commands authorize the same prepared return, including cancellation, stale candidates, preparation failure and retry. The app and actual BattleView display a separate result with a return button. Save/load preserves the receipt and serial; a subsequent encounter uses the next lease. Current owned save versions retain their existing layout, with the new explicit receipt outcome. Older readers that do not support that outcome reject it.

The same frame fence covers the force request, source VM, actions, messages and effects. A failed frame restores the request along with those owners. Successful return uses the existing joint message/effect retirement. Throwing resource cleanup is contained after publication; it cannot roll back a committed shared message or owned result.

## Native basis and remaining gates

These are static observations from the supplied `GameAssembly.dll` (`1a7e12c90c6a734e17dda507dd6ab7555090dff6a1e96f3473a90c29916ca6dc`), not dynamic original-game parity:

- External/AI Force wrappers `0xb42a00` / `0x821a50` call accessor slot21 and return Next. Save wrappers `0xb42980` / `0x8219d0` use slot22.
- EventCommand `0x1562e00` / `0x1562d90` set independent request bits. Normal enabled judgment `0x157c1f0` chooses Forced=4 before ForcedOnSave=6 and before ordinary judgment.
- Result dispatch `0x460850` sends result4 directly to WinFadeOut state13. Result6 enters state12; `0x462e90` saves parameters and recovery conditions before state13. Presentation state names do not make either result a victory.
- Escape entry `0x462d90` increments its own count. Victory entry `0x463f00` owns reward/defeat registration paths. Both forced paths bypass these entries.
- Source `GetBattleResult` `0x278b30` rechecks current Corps eligibility for previous results4/6 and may report Lose=2. The precise previous-result publication and Corps projection are not closed. A committed forced receipt therefore triggers a specific query gate; it is never mapped to Win, Escape, a fixed4/6, or an HP guess. Existing ordinary result producers retain their existing behavior.
- The save chain includes Corps rows, complete owned recovery, equipment/count reconciliation, used items and existing retained steal/drop lists. The explicit Web saved-return contract below closes the supported owner lifecycle while retaining specific gates for unimplemented writers and native previous-result queries.

`scripts/check-source-battle-forced-return.mjs` recompiles all 53 complete source battle programs (2312 instructions), preserves physical source bindings and all 490 requested parties / 483 descriptors / 7 diagnostics, and verifies the ten no-save requests. The saved-return observer below verifies the complete twenty-two-site Save family. It never executes source story programs or builds/publishes the 649 maps. Typed source sites are not playable story coverage.


## Saved forced return: declared Web owner contract

All 22 exact zero-padded `BattleForceExitOnSave` sites decode as `force-save-return` and preserve interpreter Next. Whole-source nomination is 3304 programs / 186003 instructions; the battle denominator remains 53 complete programs / 2312 instructions with 52 physical bindings and Common1 explicitly unbound. This family occurs in eight complete original bodies / 893 instructions and has 415 dependent parties among all 490 requests (483 descriptors and seven concrete failures). No body, successor or raw dependency is deleted.

A saved return requires `web-source-battle-forced-save-v1` on the encounter and its actual owned lease, as well as the existing Web battle event controls. The whole framework directory declares this in exact policy v6. Strict source directories and older policy versions receive no implied grant. Missing, unknown or misplaced declarations remain errors. `BattleGame` keeps the existing `forced` phase; the result envelope discriminates no-save4 from saved6, and Force retains priority if both independent bits are set. Save precedes ordinary win/defeat. It preserves already committed action costs and effects, suspends later actions and never generates experience, Gil, magic points, learning or escape statistics.

The Web policy writes last-entered resources once per real owned identity, including retired borrowed players. It keeps party membership and the selected saved group, and writes Front/Back for participating owners already in that selected group. This is an explicit Web alternative for the existing all-entered owned-borrow profile. It preserves actual Web battle rows rather than guessing a native preemptive row flip. The original `CorpsId` enum is Front1/Back2, while `Corps.CharacterId` is a different property. `SaveCorpList` / `SwitchByIndex` update these rows, not character identities.

Save validates actual six-slot equipment and the captured stock/occupancy closure, using full borrowed owned bindings rather than transient battle instance IDs. No in-battle equipment mutation writer is admitted; a changed loadout is a specific error. Whole-owned cleanup includes disabled and nonparticipating records in the same transaction. Native recovery retains UntilType3/19; the current condition domain supports its independently admitted persistent conditions and rejects unimplemented behavior (including unsupported UntilType19 effects). Native field-condition writers remain gated; the Save policy creates no fabricated empty provider.

`BattleRetainedLootLedger` holds existing committed steal/drop grants separately from enemy-death registrations. Native `SaveItem` consumes existing steals, then used items, then existing drops. The Web owner preserves that order, including caps and equipment occupancy. Pending registered deaths are **not** drop grants: native victory entry performs that lottery, and ForceOnSave bypasses it. The saved return never repeats the victory lottery. Actual victory still runs its existing lottery once; unimplemented source steal/drop writers retain their original gates. The ledger begins clear as part of a new real battle owner, not from a missing observation.

The common prepared GameState return transaction combines these inventory writes, parameters, rows, equipment and whole-owned recovery with shared story variables and the field continuation. Failed, cancelled and stale returns leave the same terminal battle available for retry; a committed return publishes one `forced-save` receipt and retires its messages/effects/actions. Actual completion upgrades the owned snapshot to exact version15; versions10–14 cannot carry that receipt, and version15 without an actual saved-return receipt is rejected. The receipt never counts as victory. The app distinguishes saving current state from reverting to entry state.

Static evidence adds seven bounded complete owner methods (`0x501e20`, `0x5027c0`, `0xaabbb0`, `0x455de0`, `0x1585170`, `0x764400`, `0x4670a0`) to the 24 existing methods. Raw getter bytes and all shared aliases verify UntilType index7, ConditionType index1 and the separate Corps row indirection; generic alias names alone do not establish semantics. This remains static evidence, without original-runtime execution.

These establish shared mechanism behavior; they do not establish source campaign completion, browser pixels or native parity. The parent integration owns any later whole-directory production.
