# 公共内容包的整体构建与发布

运行框架使用同一个 GameFlow、GameSession、WorldSession、GameState 和 BattleGame。内容生产也应只有一个发布边界：基础包、开发入口、系统演示、来源初始化训练场和世界旅行全部准备完成，再替换浏览器使用的公共内容集合。

入口为 `npm run skeleton:build`，亦即 `npm run content-packages:build`。它调用 [统一管线](../scripts/content-package-pipeline.mjs)，不再让六个下游 writer 逐个改写 live 目录。

## 实际步骤

1. 取得公共内容集合的构建锁。来源地点包的正常公开构建使用同一锁；第二个公开调用被拒绝，不覆盖正在运行的报告。
   编译前读取 `content-batches/source-batches.selection.json`，核验所有配方的原字节摘要、包身份和 manifest 身份；重复、保留命名或任一错误输入使整批停止。基础包正文、引用、manifest 和报告使用同一个冲突检查，不能被另一个生产器覆盖。
2. 读取受锁定的来源快照，使用当前编译器重建来源战斗能力目录与独立开发战斗目录，再编译完整来源世界、新游戏入口和 framework 派生。旧目录只用于核验旧配方和记录升级，不能作为当前能力缓存。两类世界的全部地图与入口放进同一候选集合；公开包不再借用可被独立重建的 world/framework 地图目录。
3. 原配方先核验旧绑定，再明确绑定本次候选；报告记录原配方字节摘要、每个角色的旧/新依赖摘要及来源身份，原配方文件保持原字节。基础包与普通敌队准备后，开发入口、两阶段系统演示、初始化训练场、世界旅行和声明的来源地点包并行编译。依赖普通敌队的包读取本次候选，不读取旧的独立 battle 缓存。
   共用来源敌队目录使用同一候选的全部来源地图与初始化基线，分别生产 strict/framework 正文、完整请求及诊断。原始零率引用、未知 Encount 参数和未实现区域网格继续留证。v2 来源步行配方只消费本次目录并闭合整个 set；旧目录不作为失败回退。实际消费的 import 快照及已有魔石编译证据同样进入最终输入锁。
4. 在 ignored 私有目录中组成候选集合，保留未由此次配方生产的独立包。manifest、包内 build-report 与正文一起准备；不在 import 模块时写盘。
5. 通过实际 GameContentRepository 验证所有入口，再核对目录中全部 indexed map 的摘要、map/area/source 身份，包括尚不可执行的地图。身份检查与执行准入分开。
6. 使用现有归档器在私有目录中核验完整 JSON、PNG 和 FLAC 闭包。归档不会授予来源剧情、视觉提供器或新能力。
7. 保留旧的公开版本，预检候选与已保留 CAS 的原始字节兼容，再确认来源快照、编译器、已读上游 JSON、媒体、逻辑路径绑定、配方和原公开集合没有变化。同一正文复用已验证的原始 JSON 字节，不因格式化制造归档冲突。
8. 整个候选集合一次发布；新版本归档随后完成。发布之后的归档或报告失败明确记录 `published=true`，应修复归档，不能回滚正在被游戏使用的内容并重试结算。

报告为 `build/reports/versioned-content-package-build.json`，格式 `versioned-content-package-build-v2`。它保留每个阶段、各生产器报告、整批发布状态、包清单和外部依赖数量。单独的来源批次及原剧情缺口不会因此得到准入。

## 范围与边界

此入口消费已提取的来源快照、旧配方绑定和开发入口，负责战斗能力、来源世界、来源入口、framework 与下游包的完整候选链。战斗能力更新仅允许同一来源正文、字段来源、持有初始化和媒体绑定；报告明确保留旧/新目录摘要、编译器摘要及新增加的来源引用。默认配方检查仍拒绝任意战斗目录变化，只有本次受输入锁保护的重编结果才能重绑定。原配方字节及旧版本不变，也不隐式升级存档。

原始 Unity 提取不属于此构建入口。来源正文、媒体指纹或初始化语义变化需要另行审定，不能借能力重编证明放行；未知机制仍按内容依赖准入，不能通过旧缓存或扩大规则满足新候选。

私有候选和外部输入检查防止本次构建混用代际。已发布版本的完整 JSON 与媒体由 [内容版本系统](content-versions.md) 保留；来源 export、world 或媒体目录的独立重建仍须遵守其归档规则。低层单包 writer 保留为局部开发工具，不能与公共发布并行执行。

普通公开来源批次也进入主管线；指定私有输出时仍可单独编译。新游戏与读档先选择可信版本上下文，再准备同一个 GameSession。会话的后续切图、图像和音频继续使用该版本的 CAS 对象；更新当前公共包不会切换已有会话的内容。归档缺失或角色摘要不符必须明确失败，不能退回可变 URL。

系统骨架的验收继续使用 [六组代表性连续流程](game-skeleton.md)。构建成功只证明包及资源闭包完整；探索、事件、战斗、菜单、存读档仍需通过共同运行接口的连续执行。

## 多批来源选择与统一工作单

选择文档格式为 `source-content-selection-v1`，每项包含配方路径、原字节 SHA-256 和展示标签。默认选择费加罗与南费加罗室内来源批次。可用 `npm run content-packages:build -- --source-selection content-batches/<selection>.json` 显式选择另一组；现有程序 API 的 `sourceRecipePaths` 继续支持，二者不能混用。所有所选包读同一候选世界和入口，并行纯编译后一次发布，配方与选择文档在发布前再核对原字节。

公共集合同时发布 `/content-packages/source-batches/selection.json` 与其绑定的 `work-plan.json`。前者记录本次实际选择，后者绑定同一运行时、选择摘要、原配方摘要及各批实际 manifest/dependency/content 摘要，将所有原诊断和 provider 记录按公共系统归并。每条定位保留包、批次和原索引；重复文本与未知项不去重。旧显式 API 的空选择发布 `workPlan=null`，验证器不会借用留存的旧工作单。

`npm run source-batches:check` 重新从所选公共包规划依赖，核对统一工作单，再用同一个 `runContentBatchRoute` 执行每批声明路线。所有衍生地图剥离明确的顶层开发呈现与摘要后，必须和同集合严格来源地图全字段相同。该检查保留完整诊断，只验证声明路线及原数据保存，不授予全批或完整剧情准入。

来源步行遇敌引用单独进入依赖图：map.csv 整行、对应 monster_set.csv 整行、各槽位敌队和率值保留原字符串及行证据；所有正敌队引用包含零率、未知率和未知新增槽位。时机、抽选和世界区域网格尚未实现时明确阻塞，不能因为没有显式 Encount 指令就声称地图没有战斗依赖。现有开发步行策略保持独立。
