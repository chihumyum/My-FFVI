# 复活与解除状态道具

2026-10-11，`narshe-playability-v15` 将原有道具事务扩展到不死鸟之尾和已支持状态的解除。菜单、战斗、失败重试、胜利回写和稳定检查点共享角色与库存所有权；没有给正式开场添加试验物品或增加地区。

## 来源与支持边界

| ------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 10 / 9，不死鸟之尾  | 菜单与战斗都是组 2：函数 12 解除组 428 的状态行 5、100，再由函数 34 按目标最大 HP / 8 恢复 | 支持我方复活。菜单对存活目标禁用；战斗重复复活同一目标时第二次 miss，仍消耗一件。                 |

来源是本地导入快照中的 `content.csv`、`item.csv`、`function_group.csv`、`function.csv`、`condition_group.csv`、`condition.csv` 与濒死阈值常量。库存用内容 ID，物品行和技能身份保持独立。独立检查从原始表读取预期，不从候选 `plan` 或效果计算器生成期望值；同时核对候选来源闭包的行值、对象 ID、资源包摘要与快照身份。

已有静态原生链提供以下依据：

- `OwnedItemClient.IsUseRecoveryParameter 0x7fb670` 对 FF6 的 item 行 9、10 作专门处理：第二槽函数类型 34 不参与菜单可用性判定。对凤凰尾而言，不能因为第二槽能算出 HP / 8 就允许给受伤活人治疗。行 10 的第一槽还有独立的满 HP/恢复状态分支，因此圣水需单独研究。位置见本地导出 `item-eligibility/7fb670.c:458–601`。
- `RecoveryCondition[Multi].Calc/UpdateParameter 0x66e250/0x66e910/0x66eac0/0x66f4d0` 按条件身份解除；没有匹配则 miss。状态组引用不是可激活状态的准入名单。
- `FunctionGroupInfo.HitCalc 0x8f3080`、`SetupValueToDisplay 0x4f7d60`、`BaseValueFixedHPFunction.Calc 0x4f4760` 与 `ResultValueFixedHPRecoveryFunction 0x6702d0/0x6704b0` 支持既有复活槽链、前槽 miss 传播和最大 HP 除数分支。死亡移除与最小 HP、濒死派生状态沿用 [死亡与复活](battle-life.md) 的已限定上下文。
- 菜单单次扣量及战斗使用继续沿用 [道具事务](item-actions.md)。排队预订、取消退回、400/900 毫秒展示时序与随机流仍是开发规则，未宣称与原版逐次一致。

静态导出核验保持 `semanticsVerified:false`。它证明本次读到的 C 输出、方法区间与符号来自指定 DLL，不能替代原版动态运行。

## 独立检查

先由正常构建流程生成 `dist` 和 v15 游戏目录，再执行：

```sh
node scripts/check-item-status.mjs --native /path/to/original/GameAssembly.dll
```

也可用 `FFVI_GAME_ASSEMBLY` 指定 DLL；需要可运行的 `python3`，可用 `PYTHON` 指定解释器。脚本不调用编译器、不修改候选目录或原生导出，只写自己的两份检查报告。失败重跑会清除旧成功报告，避免把过期结果当成本次通过。

29 项来源受控检查覆盖：

- 状态行 5、100 × 最大 HP 1、7、8、63、9999，分别检查菜单与战斗复活；战斗结果按不同帧切分重放相同。边界修改明确标记的完整候选副本，装备系统存在时同步其基础 HP 输入，保持装备与成长校验。
- 三组存活目标的凤凰尾菜单拒绝；万能药对满 HP 沉默角色生效，二次无状态时不扣量；山彦烟幕在菜单禁用、战斗有效。
- 两个角色预订两件凤凰尾给同一倒下角色。第二次结算仍指向原对象，所有效果 miss，最终只恢复一次 HP、消耗两件。
- 菜单使用后编码/恢复检查点 → 受控战斗使用 → 受控失败 → 重试恢复入场角色和数量 → 再次复活与解除沉默 → 受控敌人 HP 归零 → 胜利仅回写一次 → 检查点再次编码/恢复。
- 未实现活动状态仍被恢复入口拒绝。毒、黑暗、石化、僵尸等的状态引用没有被当作行为支持。

这里的 HP、状态、库存、准备完成的行动条与战斗结束是明确构造的机制输入；不会证明故事获得途径、敌人实战胜利或新增可玩地图。来源奖励 Gil 另从 `monster.csv.gill` 读取校验，避免用候选奖励值自证。

`build/reports/item-status-check.json` 绑定来源集、原始战斗包、候选目录、原始及受控字段包、原表定位、29 项输入与结果。`build/reports/item-status-native-check.json` 重新核对六批现有导出的 42 个方法：完整 DLL、符号/header、唯一方法身份、下一符号边界、PE 源字节区间与完整 C 文本摘要。方法区间可能含对齐字节，不是精确源码函数长度。

原版动态一致性仍未进行，不能由这些静态与受控检查替代。完整状态引擎、敌方道具/不死目标、装备永久状态恢复、帐篷/永久成长、完整物品事件与全游戏迁移仍不由这组检查证明。
