# 来源战斗效果与同步

全源提名使用全部 3,304 程序、186,003 指令，保留 53 个战斗脚本的 2,312 条原正文、490 个敌队请求、483 个来源描述及 7 个原始诊断。PlayBattleEffect 有 143 站点、13 个程序；SyncBattleEffect 有 41 站点、11 个程序；两族并集是 13 个完整程序、1,227 条正文。完整数据与其它脚本缺口不因这批解码而删减。

PlayBattleEffect 的 i0 为 1 时，i1 是玩家的 CharacterStatus 身份；来源其它已观察值 2 使用敌人的 unique 槽位。它不是队伍序号或位掩码。i2 绑定原 battle_effect_asset.csv 行和三个 SE 依赖；缺失行、空资产名和无效身份拒绝编译。完整原行、物理文件、对象 ID、CAB 和行 ID 保留在 typed 操作中；内容源集合及文件摘要仍由原编译链绑定。效果不产生 HP、MP、条件、能力、剧情旗标或队伍结果。

原 wrapper 的 i3 非零是异步 Next，0 是同步 Blank；实际 Core.get_Next 为 0、get_Blank 为 1。读取 C 中的 0/1 时曾发生反向解释，ignored 提案及修正记录分别保留，产品只使用复核后的极性。同步第一次发出请求后等待下一时钟；后续与 SyncBattleEffect 一样查询全局列表和效果父级，不只等待最近一个 ticket。

BattleGame 是唯一逻辑效果 owner。VM 只保留 PC 和 wait，沿同一 BattleGame 原有 10ms 时钟查询完成状态。一个 prepared resource lease 只持有媒体准备状态，不持有游戏队列、计时器、目标、计算结果或第二个 Field。资源准备和发布与既有 VM、行动、费用、RNG、单位、消息 frame 一起提交；失败回滚本帧，候选资源取消，重试不产生两条已发布请求。目标在发出时绑定实际战斗实例；同身份替换实例不能接走旧效果。

资源 `discard` 可以抛错，不能作为逻辑事务的提交步骤。消息 frame 发布后，完成资源才逐个尝试清理；失败只进入不可变 `effectCleanupFailures` 诊断，剩余 lease 仍继续清理，不回滚已发布消息、VM 或 UI mask。失败帧先恢复所有 BattleGame owner，再逐个清理新候选；清理异常不替换最初的提交异常。返场和重试先提交消息退休，再退休效果 owner；退休后清理失败仍不能让旧回调重新绑定新战斗。清理失败代表媒体释放未获确认，不计为来源剧情通过，也不宣称媒体已成功释放。

生产 App 与来源 Web 回放显式选择 `web-source-battle-effects-pulse-v1`。这个策略以一次资源准备阶段和 300ms 平面脉冲表达效果，使用同一 BattleGame 时钟，原生 prefab、音效、材质、粒子及准确时长均后置。它不会把“有 master 行”说成已还原原生资源。真实来源的资产引用继续保留；缺行或空名称仍是缺口。严格调用者不选择此策略即拒绝，而存档不能授予策略。

同步观察全部待准备/正在呈现的效果，也观察原有行动的正在呈现阶段，不将普通待执行队列误称为正在显示的效果。暂停停止同一逻辑时钟。BattleView 只读取不可变投影画脉冲，不写模拟状态。成功返场或固定入口重试通过原 GameSession 事务退休旧效果并取消资源；取消交接保持旧战斗。旧 resource 的迟到准备完成不能触达新战斗，退休的 VM 不能继续推进。活动战斗仍不进入稳定存档，返场后的存读档使用原有 owner 和 codec。

`check-source-battle-event-effects.mjs` 复用现有完整来源 Session/敌队目录检查器，不启动另一个 649 图生产器。它使用同运行时的统一 candidate，保留所有 53 个战斗程序与 490 个来源敌队请求；参数解码、实际完整程序执行、合法结算、Storage、App、浏览器和原生对齐分别报告。来源 flags、其它 SysCall、AI、资源和入口依赖仍会阻塞；本批机制测试或 184 站点解码不代表全部战斗、剧情或 Web 迁移完成。
