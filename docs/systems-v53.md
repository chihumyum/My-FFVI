# v53：战斗事件生命周期

本轮把战斗根脚本接入现有游戏骨架。脚本负责启动和轮询敌人 AI、等待行动、控制交互与结束许可；战斗结束后继续走同一条奖励、返场和存取链。没有为具体敌队或地图增加运行时分支。

## 所有权与内容合同

`BattleEventProgram` 是带来源身份的类型化程序，保留原 PC 和未知指令诊断。纯解释器只持有 PC、调用栈、脚本局部整数和等待状态；每次返回至多一个宿主请求，宿主在同一帧处理后提供新上下文。它不拥有敌人、动作队列、角色或随机流。

`BattleGame` 拥有根程序的执行状态、控制许可和现有敌方 AI。启动 AI 复用原解释器及其独立行为变量；同步查询真实单位条件和全局动作队列，不另建一套敌人状态。普通行动、反击、根脚本和结算共用既有帧事务；异常回滚 PC、许可、角色、队列、随机数与逻辑时间。重试使用入战时固定的程序，从入口重新开始，不读取后来被修改的内容对象。

每个新编译的敌队都明确声明 `battle-lifecycle-v1`：

- `none`：来源敌队没有根脚本。
- `script`：完整程序已通过结构和指令检查；运行仍需满足单位、条件及结果提供器的上下文。
- `development-omission`：保留原有、精确来源绑定的开发省略及原因；不能当作无脚本，也不能进入严格来源批次。

来源目录必须逐敌队声明生命周期，公共目录不能代填。批次依赖同时验证程序与当前条件规则；已解码报告不能绕过运行合同。严格来源仓库的新游戏和来源存档恢复也拒绝开发省略，只有明确的框架 profile 与开发片段可继续使用它。编译器以 `script.csv` 和精确资产路径建立身份，JSON 中复制残留的 `Name` 不作为来源索引。未知 SysCall、全局变量类别及未恢复的头部能力仍保留阻塞。

## 时钟与终局

Web 开发宿主使用同一 10ms 时钟，顺序为行动与进度 → 根脚本 → 结束判断；构造完成后执行 clock 0，并显式视为战斗已开始。这是当前宿主协议，未证明与 Unity 各组件的帧次序一致。

`SyncBattleAI` 每次写入局部槽 0 后继续，等待由脚本自己的 Blank/Branch 构成。单位满足结束条件后，还要等全局 staged、normal、interrupt 队列全部排空，才结束对应 AI 核。`BattleSyncAction` 则只等待当前行动和反击队列，不等待普通排队行动。

脚本 Pause 停止进度与新普通行动；当前行动、反击和根脚本继续运行。Interactive 只控制玩家命令输入。暂停期间仍执行等待、解除暂停及结束许可，避免撤退或收尾脚本卡住。

结束许可初值为 true，但不能替代根程序状态。关闭许可时暂不结算；开放后，玩家全灭优先败北，不要求根脚本退出；正常胜利必须等根程序退出。根程序提前退出而敌方仍存活时，当前宿主明确拒绝尚未准入的结果提供器，不能按旧的全敌倒地规则发放 EXP/Gil。全敌倒地的已支持结算继续复用原事务，无脚本和显式省略模式保留开发规则。

原生条件驱动的逃离、强制结果和动态单位更换仍未恢复；显式开发撤退继续使用既有独立策略。重复 Exec 的混合运行/休眠 AI 核也未准入；当前固定单位宿主拒绝重复启动已有活动核。这些是宿主边界，不是声称原版具有同样限制。

## 验证

`npm run battle-lifecycle:check` 运行原生静态绑定和完整来源程序的连续检查；`npm run framework:verify` 将生命周期纳入现有系统套件。

原生检查绑定 9 份既有反编译回执、50 段原始字节及 13 组语义断言，见 [来源与宿主边界](battle-event-source.md)。53 个脚本资产、490 个有脚本敌队引用仅用于依赖分析，不能计为运行覆盖。未执行原版，`semanticsVerified` 仍为 false。

本轮最终全量 TypeScript **2,239/2,239**、registry 与 Python **39/39** 通过。针对新解释器、编译器和战斗接缝的检查覆盖暂停、反击排空、根退出、结束许可、全灭优先、撤退恢复、帧切分、失败回滚、重试固定程序及返场后的存取。系统套件 **26/26** 通过，含生命周期 **10 阶段**、浏览器入口受控检查 **14 项**及 **138 个**实际模块的依赖图。来源目录 **10 项 / 2 条旅程**、普通 AI、反击和计时回归也通过。

完整来源代表为 `script.csv:9001 → sc_b_2001` 的 12 条原始指令，原始引用者是敌队 442。连续检查将完整程序绑定到私有敌队 3002 副本；该敌队原本 `script_name=0`，其来源敌人、AI、能力、媒体、编组和奖励保持原定义。原始敌队 442 的媒体等缺口仍单独报告。这个组合验证框架接线，不授予 442 或其他未闭合敌队运行资格。

连续检查在同一个会话中完成两场胜利，中间经真实 `CheckpointStorage` 编码、写入、读取和恢复。两场根程序分别经过 **641 / 599 个** Blank 轮询时钟后退出，局部槽 0 变为 1，奖励只发布一次；另用明确合成的尾部程序验证末击后继续等待结束许可，期间持有角色不被提前改写。

浏览器实际执行两步移动入战、两次火炎射线、胜利和返回，再保存、刷新、继续。结果页为 **96 EXP / 96 Gil**；恢复后的 **3,096 Gil**、位置 **(38,49)**、等级 **3/2/2**、HP **63/63/37**、最大 HP **63/79/81**、MP **27/0/0** 与保存前一致。修复后未捕获警告或错误。浏览器使用独立本地端口和私有内容组合，未使用用户现有进度；核内 PC/AI 的采样由连续检查覆盖，浏览器只确认可见流程与结果。证据为 `build/reports/v53-battle-lifecycle-browser-check.json` 及对应胜利、读档截图。公共内容只通过编译器生成，受控组合输出至 ignored 目录。

首轮浏览器验证发现新 VM 的 Node 包导入使原生浏览器 ESM 停止加载，因此运行时校验改为项目已有的纯本地验证方式。入口检查器新增实际浏览器模块图解析检查，已用首次失败复现验证它能拒绝这种依赖；Node DOM 测试不能替代浏览器加载。旧目录回归还发现其受控编译输入的省略说明与真实目录不同，已改为传递同一来源绑定的说明，保留完整输出比较。

来源目录、新游戏包及框架包已重新编译。最终运行摘要为 `174d88602413ba2bb51f7b2485193da24ccd28def5f73c3e8a8c8e1122ab8072`，系统套件、浏览器和批次检查绑定该构建。来源批次仍有 **33 条内容诊断及 5 条路线准入阻塞**：开发来源旅程 609→3→178→609 在 80,550ms、`sc_e_0001_3:154` 停止，`readyForBatchPopulation=false`。严格来源新游戏/读档现在会先拒绝目录中的脚本省略；以上旅程仍是显式 framework profile。没有宣称完整开场或主线可玩，也未把摄像机细节改列为下一系统任务。

## 接续范围

下一系统增量是战斗脚本与共享角色/剧情状态之间的读写接口及事务边界，再接其实际使用的公共系统调用。优先解决可复用的能力组合、失败恢复与结果提交，随后按依赖闭包填充内容；不把每个敌队、地图或演出细节变成独立实现任务。常用 `sc_b_0239` 的 Gau、Shadow、血涂盾等真实副作用仍显式缺失，不以空操作换取批量通过。HD-2D 和精细表现继续后置。
