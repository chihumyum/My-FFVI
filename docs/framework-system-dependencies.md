## 已交付：共用普通手动消息

普通 `window=0/3, r0=0` 的静态正文／说话人及显式 `<P>` 页已经由共用 compiler、FieldGame 和 UI 接通，详见 [同步字段对话](field-manual-message.md)。本轮准入 3510 处，包含 533 处显式多页调用。任务所有权、开始／关闭掩码、保留提示转选项、异步字幕交接和重复确认都有回归。

初始盘点曾怀疑窗口 1/2 与说话人是主要缺口；原始数据不支持这一优先级：4615 处中窗口 0 有 4020 处，窗口 3 有 592 处，窗口 1 仅 3 处，窗口 2 没有。已有说话人 2415 处为普通静态文本，2149 处为空，51 处缺本地化。因此先补普通控制器与明确分页，比建立小众窗口系统能覆盖更多调用。

下一层消息需求应按参数族推进：窗口 0/3 分别有 39/29 处正时长调用、24/19 处负时长调用；内联 WAIT、AUTO、PRESS、CT 与动态替换不允许剥除。`sc_e_0001_3:26` 等若干正时长 `.01` 调用仍阻塞，不能将 `.01` 改写成手动确认或猜成字符间隔。继续时应复用同一个消息所有者，增加明确的计时／完成策略；不要为每个 key 写处理器。

## 下一完整增量：交通生命周期

当前最早实际阻塞是 `Map_40037/sc_e_0001_3:4 SetVehicle`，其后 index 5 为上乘魔导装甲，index 6–8 为来源 puppet 的 `RideVehicleNPC`。这是三个不同操作，不能只把 `transportationId` 或贴图改成 6。

已有 [交通模块](transportation.md) 提供无状态的身份、启用标记、`projectChange` 和 `projectMapEntry`，字段毒等系统已读取交通身份。来源链已区分：`SetVehicle 0x2cb2b0 → TransportationEnabled 0x2f1fe0` 启用并设置交通数据；`GetOnMagitekArmor 0x27a190` 调 `ChangeTransportation(6,true,false,0)`；`RideVehicleNPC` 修改角色骑乘结构，本身不证明当前交通被切换。

现有宿主还缺可变生命周期：

| 所有者或接口 | 当前边界 | 下一步应承担的职责 |
| --- | --- | --- |
| `GameState.sourceNativeState` | 持有交通与停放地图只有初始化值；校验拒绝未实现变更 | 通过同一 owned 草稿保存来源已恢复的停放数据，不另建交通库存 |
| `EventState` | release flag 已能精确读取，未知保持未知 | 启用操作与停放记录同事务提交；不复制一份 enable 布尔值 |
| `FieldGame.transportationId` | 只读，恢复绑定可信入口身份 | 实际当前交通的唯一可变 owner，并与演员／碰撞／操控状态一起准备发布 |
| 原生 `actors` 与 `FieldPartyActors` | 已有身份、位置、内外层资产和刷新事务 | 上／下乘更新同一演员实例与候选外观；保留源 selector 到实例的映射 |
| `WorldSession` | `projectMapEntry` 能选身份，但改变身份仍显式阻塞 | 切图候选消费同一交通状态，完整准备后提交；旧候选不能覆盖新状态 |
| 保存与返场 | 交通只能还原已准入的入口值 | 验证当前交通、启用标记、停放记录、骑乘外观的一致性，而非接受存档自报 |

最小完整契约建议分三类来源命令：放置／启用交通、玩家上落乘、NPC 骑乘。它们分别生成纯候选，宿主统一准备媒体、演员、camera、碰撞与移动监视器，再使用现有 `prepareFieldState`／验证后 `commitWith` 的方式一次发布。候选不得另存一份持续演员集合；字段状态、毒步伤、菜单资格、入战、跨图和保存都读取这个实际交通身份。

停车完整字段与某些表现回调尚未闭合，须在实现该增量时明确列出；不能由初始化的 `parkedTransportationMapIds=-1` 推造方向或坐标。来源 6 的 release flag 是 `TreasureFlag4[137]`，不是后续脚本的 `ScenarioFlag4[132]`。负 actor selector 也不是 Web 实际玩家 id，必须走现有绑定。

## 之后的框架接缝

1. **事件内自动保存与结束。** `sc_e_0001_5:18 AutoSave` 处仍在脚本任务中，而当前稳定 checkpoint 明确拒绝活动任务。需要可准备、可失败、恰好一次完成的保存协议，或有来源约束的保存边界与继续帧；不能把当前 stable-checkpoint API 强行调用，也不能自动清空任务。
2. **标题／帮助的共用完成信号。** 同脚本 index 16/19 的 `ShowMapTitle`、`ShowHelpAndExit` 需把实际等待／结束投影接入既有 Flow 和任务所有者。地图标题是高频共用 UI；帮助／退出只有一处，应独立记录，不能让无回调的空操作假称完成。
3. **来源 SE 生命周期。** `PlaySE/SyncSE` 应共用既有媒体准备与任务等待端口。需要明确 channel、循环、停止、失败和 stale completion；显式开发静音必须保留 omission 与等待策略，不扩成音频底层研究。
4. **故事入口与战斗返回。** 现有遭遇目录、候选战斗、奖励成长和来源返场已能在受控连续流程验证。新剧情只填编组与 continuation 的前提是这些引用和来源资格被同一编译器诊断；不能复用旧三人开发检查点代替真实开场持有状态。

这些候选按实际路线与复用率排序，仍需分别限定能力和验收，不能把静态后继写成已完成队列。框架持续验收以 `npm run framework:verify` 和 [v43 系统记录](systems-v43.md) 为准；严格来源、开发派生、受控会话、浏览器和原版动态证据始终分开。
