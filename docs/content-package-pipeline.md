# 公共内容包的整体构建与发布

运行框架使用同一个 GameFlow、GameSession、WorldSession、GameState 和 BattleGame。内容生产也应只有一个发布边界：基础包、开发入口、系统演示、来源初始化训练场和世界旅行全部准备完成，再替换浏览器使用的公共内容集合。

入口为 `npm run skeleton:build`，亦即 `npm run content-packages:build`。它调用 [统一管线](../scripts/content-package-pipeline.mjs)，不再让六个下游 writer 逐个改写 live 目录。

## 实际步骤

1. 取得公共内容集合的构建锁。来源地点包的正常公开构建使用同一锁；第二个公开调用被拒绝，不覆盖正在运行的报告。
2. 读取受锁定的来源快照，纯编译完整来源世界、新游戏入口和 framework 派生。两类世界的全部地图与入口放进同一候选集合；公开包不再借用可被独立重建的 world/framework 地图目录。
3. 原配方先核验旧绑定，再明确绑定本次候选；报告记录原配方字节摘要、每个角色的旧/新依赖摘要及来源身份，原配方文件保持原字节。基础包与普通敌队准备后，开发入口、两阶段系统演示、初始化训练场、世界旅行和声明的来源地点包并行编译。依赖普通敌队的包读取本次候选，不读取旧的独立 battle 缓存。
4. 在 ignored 私有目录中组成候选集合，保留未由此次配方生产的独立包。manifest、包内 build-report 与正文一起准备；不在 import 模块时写盘。
5. 通过实际 GameContentRepository 验证所有入口，再核对目录中全部 indexed map 的摘要、map/area/source 身份，包括尚不可执行的地图。身份检查与执行准入分开。
6. 使用现有归档器在私有目录中核验完整 JSON、PNG 和 FLAC 闭包。归档不会授予来源剧情、视觉提供器或新能力。
7. 保留旧的公开版本，预检候选与已保留 CAS 的原始字节兼容，再确认来源快照、编译器、已读上游 JSON、媒体、逻辑路径绑定、配方和原公开集合没有变化。同一正文复用已验证的原始 JSON 字节，不因格式化制造归档冲突。
8. 整个候选集合一次发布；新版本归档随后完成。发布之后的归档或报告失败明确记录 `published=true`，应修复归档，不能回滚正在被游戏使用的内容并重试结算。

报告为 `build/reports/versioned-content-package-build.json`，格式 `versioned-content-package-build-v2`。它保留每个阶段、各生产器报告、整批发布状态、包清单和外部依赖数量。单独的来源批次及原剧情缺口不会因此得到准入。

## 范围与边界

此入口消费已提取的来源快照、已验证来源战斗目录和旧开发入口，负责来源世界、来源入口、framework 与下游包的完整候选链。战斗目录在本轮明确复用；原始 Unity 提取和全部战斗目录重建仍不是该入口的工作范围。来源或媒体指纹变化不是同一次配方重绑定，必须重新审定来源；不能使用旧缓存或改变初始化语义满足新候选。

私有候选和外部输入检查防止本次构建混用代际。已发布版本的完整 JSON 与媒体由 [内容版本系统](content-versions.md) 保留；来源 export、world 或媒体目录的独立重建仍须遵守其归档规则。低层单包 writer 保留为局部开发工具，不能与公共发布并行执行。

普通公开来源批次也进入主管线；指定私有输出时仍可单独编译。新游戏与读档先选择可信版本上下文，再准备同一个 GameSession。会话的后续切图、图像和音频继续使用该版本的 CAS 对象；更新当前公共包不会切换已有会话的内容。归档缺失或角色摘要不符必须明确失败，不能退回可变 URL。

系统骨架的验收继续使用 [六组代表性连续流程](game-skeleton.md)。构建成功只证明包及资源闭包完整；探索、事件、战斗、菜单、存读档仍需通过共同运行接口的连续执行。
