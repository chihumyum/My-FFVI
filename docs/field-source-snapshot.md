# Immutable owned Field source snapshots

`sourceSnapshot: 'immutable-owned-field-source-v1'` is an explicit runtime input ownership mode. It grants no source instruction, content profile, board, media, native phase or save permission. The existing constructor behavior without this option keeps mutable public content and complete repeated validation. Caller objects are never frozen or modified. Source snapshots accept plain records (including null-prototype dictionaries), ordinary arrays and immutable scalar data; optional undefined values remain supported. Map, Set, Date, buffers, typed arrays, custom instances, accessors, symbolic properties and cycles are rejected explicitly. Validation occurs before and after cloning; null-prototype dictionaries remain null-prototype in the owned copy.

In the new mode, FieldGame takes a detached source snapshot at construction and exposes the actual immutable owned content through `field.content`. Both nested writes and replacing that property fail. Source changes use the existing new map/replacement preparation, which performs new full admission. Modifying the original caller after snapshot creation deliberately does not rewrite the live source under this explicit API. This is a visible snapshot contract, not a hidden cache of a mutable input.

Complete source admission validates the existing logical, flat and transform policies, all raw rows and diagnostics, exact source membership, media and current map/entity/geometry bindings. The owned directory and per-Field source are deeply immutable. Internal indexes and comparison peers refer only to those genuine owned admissions. There is no unchecked admission constructor or public boolean to skip validation. Standalone public projection and mutable APIs still perform their original full checks.

The motion path resolves the exact current definition/ref/instance against this admission while continuing to validate the actual manager/map, board lifetime token, camera, task, position, clock and runtime authority. Existing lease and host callbacks are followed by these live checks before publication. Reusing a source admission never makes an old board instance current, so same-id destroy/recreate, map retirement and late completion still fail. Runtime removal/change of source or transform authority is rejected.

WorldSession uses the same mode for the initial manager, map candidates and restored manager; GameSession forwards the fresh trusted runtime choice. New candidate catalogs are fully admitted before the owned commit fence and installed only on successful publication. Candidate discard or false owned commit does not replace the live source. A throwing opaque host commit remains terminal and cannot be described as rollback. Real host reentry may commit its own state and makes the outer draft stale.

App and the shared positive Web replay helper explicitly select the same mode. No content schema/profile version or checkpoint shape changes. Storage records state and existing source references, not a snapshot capability. Restore checks the trusted source anew and requires the fresh runtime choice; injecting a snapshot property into a checkpoint is rejected. Restoring without the option retains the old mutable mode.

Validation covers complete-directory strict/admitted binding equivalence, unknown/mutated source data, writable detached caller versus actual immutable content, host writes in prepare/validate, runtime authority removal, actual instance replacement, failed/cancelled map preparation and retry, map retirement, a real prepared battle with failed/cancelled entry and one terminal return, Storage, false owned commit, opaque commit failure, and host reentry. Original directory rows and remaining unknown gates are preserved.

Ignored measurement receipts compare the same 649 map sources, 914 raw objects and 73 ready bindings. Actual FieldGame, Puppet VM and 10ms updates consume original Lerp parameters through a controlled caller. Exact prefix states and source hashes must agree. A separate after-only full-duration run advances every update through the 117-second command; it does not count as original source-body execution or continuous original new-game play. CPU and wall time, one-time admission cost and remaining limitations are reported separately.
