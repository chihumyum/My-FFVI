# 来源粒子启动、时间与容量

这一层恢复当前五个来源发射器使用的循环、预热、增量模拟分支。它只产生候选状态与有序步进计划，不拥有粒子数组，不单独放行完整发射器。出生、运动、死亡排列、几何和共享效果事务必须在同一宿主候选中执行完毕才能发布。

## 时间来源

`tools/export_field_particle_clock.py` 从 `globalgamemanagers` 的 `TimeManager` 对象 `8` 导出四项独立设置。文件 SHA-256 为 `bc33b3eaaab47d14fbbf792f5bcc664c7e2f4787376449306739bce658dc7881`，对象 ID 保留为字符串。来源值分别为 float32 的固定步长 `0.02`、最大粒子步长 `0.03`、最大允许帧间隔 `0.1`，以及时间倍率 `1`。

`GetTimeStep`（`0x18e750`）在游戏正在运行、使用缩放时间的分支中，固定模拟读取固定步长。普通帧超出最大粒子步长时，先计算 `ceil(delta / maximumParticleTimestep)`，再均分整个间隔；`delta=0.1` 因此产生 `0.025`，不能直接截为 `0.03`。计算保留来源 float32 的舍入次序。输入是引擎已取得的时间，不把浏览器墙钟直接当作来源时间；最大帧间隔的取得与应用仍由宿主处理。

## 预热和启动

`ComputePrewarmStartParameters`（`0x189920`）从最大生命周期、固定步长和请求时刻计算预热长度与循环起点。当前五个发射器的最大生命周期分别是 `5`、`3.5`、`0.64`、`0.64`、`0.64` 秒，零时刻启动的起点分别是 `0`、`0.5`、`0.36000001430511475`。预热长度不能固定为一次循环。

该函数还使用临时发射状态运行一次试算。`prepareParticlePrewarm` 将这些区间作为独立结果保留，不能把试算后的随机流写入真正的发射器。后续模拟中的浮点余量与循环边界也原样保留，不能为了显示整齐强制归零。

已通过实际指令验证的停止态启动链是：

1. `Play(true)` 调用 `ResetSeeds`。
2. 开启循环预热后进入 `Simulate(0, restart | fixedTimeStep)`，再次重置种子并清空粒子。
3. 内部 `Play(false)` 第三次重置种子，然后按预热计划调用固定步长更新。
4. 外层恢复播放状态。

自动种子模式下三次重置都消费同一个 manager 随机流，首粒子使用第三次种子。显式种子模式保留给定种子，不消费 manager。`prepareStoppedParticlePlay` 返回这条有界路径的随机候选、起始状态和模拟计划；它不把一次 `ResetSeeds` 误当作完整启动，也不覆盖恢复播放、禁用对象或任意 seek 的分支。系统熵仍须由明确宿主提供，来源序列化的零不能替代它。

## 更新与出生容量

`Update1b → Update1Incremental`（`0x197820 → 0x1972a0`）保留 accumulator。固定模拟等待完整固定步长；普通模拟用来源 epsilon 判断剩余间隔。每个切片先推进系统时钟，再更新已有粒子，最后处理该切片的新生粒子。连续发射与 burst 保持自己的随机顺序；跨度达到一个循环时使用来源的微小时间偏移，不能把首尾相同误认为没有经过时间。

超过 5 秒和 10 秒的追赶分支分别可以增大步长至 `0.2` 和 `1` 秒，并保留前一切片的选择；标志位允许关闭这种增长。切片结果保留 `frameOffset`，供出生时的运动补偿使用。受支持工作量有显式预算，数值溢出或精度不足以继续推进时拒绝整个候选。

`reserveParticleBirthBatch` 对应普通 `ringBufferMode=0` 的 `AddNewParticles`（`0x186c80`）：容量按真实活动数计算，新生写入起点与临时尾部按四 lane 对齐，预留容量按 32 对齐。填充 lane 会参与 SIMD 运算，却不是活粒子。出生完成后还需要来源压缩顺序，将对齐临时尾部移动回实际尾部；本函数只给出分配计划，不能代替数组拥有者。容量降低到现存数量以下时不凭空删除已有粒子。

`prepareParticleBirthTiming` 将发射结果与接受数量转换为逐粒子的出生时间。连续发射使用相对索引、分数余量和 spacing；burst 在 mask 阶段清零后仍执行来源 `maxps`，其常量是 float32 `1e-6`，不是零。因此一个 `0.03` 秒切片中的 burst 仍得到约 `3e-8` 秒的出生子步。规范发射时间由当前时刻减去本切片时间后插值，并夹到 `[0,1]`；跨循环时不能直接用已经循环归一化的旧时刻替代。这里只准入实际来源的一秒 duration，其他时长的倒数归一化仍拒绝。

该接口经 96 组完整 `StartModules` 时间循环的隔离执行对照，保留了不满四 lane 的批次、连续与 burst 混合、容量截断以及跨零时刻的插值。模块计算由惰性受控回调代替，粒子数组只提供零速度和不会过期的状态，因此这项检查不证明完整出生运动或死亡排列。

## 证据与检查

引擎身份沿用 [粒子引擎](field-particle-emitter.md) 的精确 DLL/PDB。两批生命周期导出、既有种子和出生上下文导出共同绑定 44 个方法，编译器要求其中 16 个相关方法的精确字节摘要。隔离探针执行源 `Play`、`Simulate`、`Clear`、种子重置、预热、调度、容量和出生时间指令，外部时间、活动场景对象、空 subemitter、禁用可选模块、分配、变换、通知和模块调用均明确标注为受控提供器。

```sh
.venv/bin/python tools/export_field_particle_clock.py --source build/runtime/game --output build/v36-field-particle-clock
npm run field-particle-lifecycle:check
```

本批原指令对照包括 28 个步长、21 个预热、48 个调度、54 个容量、8 个启动序列和 96 个出生时间，共 255 组。原生绑定 269 项、来源检查 521 项通过；生命周期自身 18 项语义测试与既有发射器 13 项回归通过。两项 Python 测试检查设置丢失、非法数值和未恢复的归一化分支。

报告位于忽略目录 `build/reports/field-particle-lifecycle-*`。它们不是 Windows 游戏运行、浏览器完整粒子帧或全流程验收，继续标注 `semanticsVerified=false` 和 `admittedFullEmitters=0`。来源开场仍需把这些模块接入完整宿主。
