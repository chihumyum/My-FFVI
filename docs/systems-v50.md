# v50：通用编组与入战框架

这轮继续优先搭建游戏系统。敌队资格、阵型选择、战斗运行和画面布局各有一个职责，不随地图或敌队编号增加分支。既有探索、战斗、奖励、返场与存读档闭环继续使用同一会话。HD-2D 和精细原生演出仍后置。

## 内容到运行的合同

1. 来源编译保留 `monster_party` 的全部六位阵型资格，以及九个稀疏成员槽的身份、组别与原始坐标。资格不是概率；导入不会选择第一个类型，也不删除未支持类型。
2. `BattleFormationPlan` 描述固定阵型，或完整资格加上明确编写的 `FrameworkBattleFormationPolicy`。没有选择提供器的多候选继续阻塞。开发规则只能给已实现的来源列 1/3 正权重，其他类型明确拒绝，强制 SideAttack 旗标 27 也不能通过省略名单绕过。
3. 动态运行定义的 `formation=null` 表示尚未选定。`encounterContent` 依据会话种子解析为一次 `BattleFormationChoice`，才可交给 `BattleGame`。直接把未选定义交给战斗构造器会失败。
4. 会话从原有 seed/encounterSerial 派生战斗种子。阵型抽选用版本化、独立的开发随机流，不消耗行动或步行遇敌流。只在战斗完整构造成功后发布并推进序号；失败保留请求。败北重试复用已解析内容和原始种子，不再次选阵型。
5. 保存仍使用 v5，无第二份随机计数。可信目录摘要绑定资格、权重和策略 ID；保存恢复后由同一 seed/serial 重现后续选择。来源新游戏及来源批次拒绝开发阵型策略。

普通固定条目保持原路径；现有 `pattern3 → opposed` 仍是开发投影，不宣称侧击物理、原生初始 ATB、先制/背袭及其目标分组已恢复。针对 `normalFormationOnly` 的动作，批次检查所有可能到达的阵型，不能以一次随机落在普通分支就宣称依赖闭合。

## 共用布局

`projectDevelopmentBattleLayout` 将当前战斗单位投影到 512×288 的可用网格，最多四名玩家、九名敌人。普通布局按阵营；opposed 按敌人 group1/2 分翼，多个右侧成员各有位置。单位身份、输入槽顺序和玩家前后排保留，死亡不导致邻居重新排位。地面锚点限定在 y≤155，为桌面四人菜单留出空间；可变菜单高度在其他视口下仍需独立验证。

`BattleView`、正式页面及两个工作台注入同一提供器。Renderer 不抽阵型、不更改成员、不按敌队编号调整位置。缺少提供器或单位位置时明确失败。这是可复用的开发显示合同；原始 x/y 仍保留在内容中，不把网格称为来源视觉一致性，也不保证任意超大图像互不遮挡。

## 来源证据与边界

本地默认遇敌表盘点为 205 张地图、96 个敌组、259 个正权重敌队；其中 254 个允许多种阵型。此前单阵型导入限制会在资源、脚本等检查之前拦住这些描述。解除导入限制只让诊断进入后续依赖，不代表新增可玩敌队：251 队有非零 `get_value`、220 队带旗标、257 队带战斗脚本。

本构建 `BattlePopPlug.Calculation 0x6743d0` 的静态证据将列 1/2/3/4/5/6 分别关联到 Normal/BackAttack/EnemySideAttack/SideAttack/PreeMptive/EnemyPreeMptive。`GetWeight 0x6746b0` 使用单位与装备上下文，`InitBattleFormation 0x45f2c0` 另处理强制旗标。开发权重没有替代为所谓原版概率。本轮没有新增原生导出或原版运行验收。
