# v70 完整持有名册与三组编队菜单

本批继续系统优先：将已有名册、三组四格、演员、战斗与保存接成可操作的编队系统。既有系统演示入口保留，原版剧情和 HD-2D 不因此放行。

## 用户操作与状态所有权

暂停菜单的“队伍与能力”可浏览三组编队、为每个位置选择实际已持有且 enabled 的角色、移出成员、设置排位，再明确选择当前队伍。浏览一组不会切换当前组。当前组必须保留成员，同组不能重复；其他保存组保留既有允许重复持有身份的语义。

菜单始终按 owned 身份修改格位。来源角色模板、名册中的持有对象和战斗实例不是同一个身份。编队操作不执行 Join、Unlock 或启用，不重置 HP、MP、装备、能力和成长，也不重新发放装备。未持有与 disabled 成员不能通过菜单取得资格。

`PartyMenuChange` 新增两种明确输入：

- `set-member {slot, position, ownedId, row}` 编辑某组某格；`ownedId=null` 表示移出该格。
- `select-slot {slot}` 选择已配置且可用的保存组。

原排序和前后排操作保留。界面按钮继续携带渲染时的完整三组 `expected`，通过 `GameCommands.changeParty` 提交；旧按钮不能覆盖任何组的较新编辑。批次声明输入通过同一 `GameMenuCommand` 解析与命令接口。

## 共同事务与依赖

`GameState.preparePartyMenu` 准备原持久 owner 的候选格位与 detached 玩家投影，不开启 battle lease。`GameSession.changeParty` 复用原演员准备与同步发布：状态和演员全部验证，确认原 Flow 所有者及输入仍有效后才提交。

未选中的保存组不因未来战斗依赖而禁用数据编辑；完整演员上下文仍按实际字段宿主联合准备。新操作改变活动成员或所选组时，复用当前字段资格、条件、持有指令与必要媒体检查。已知临时不可行动与未知能力提供器分别处理，不要求所有潜在技能均实现。实际选组缺少必要依赖时保留原队伍和外观。

候选成员和入战共用 `battleUnitMediaUrls` 的单位姿态闭包；菜单没有遭遇，因此不构造假背景或敌人。`battleMediaUrls` 继续增加本场背景、敌人与注册增援。同一媒体验证不对未使用模板产生依赖。

`GameState` 仍是名册和编队的唯一持久 owner，存档格式保持 owned v12 / game-checkpoint v5。恢复不重跑加入、地图初始化或发奖；下一战从恢复后的 selectedSlot 冻结实际成员、格位与排位。

## 验证范围

`npm run party-organization:check` 使用实际来源初始化、普通敌队及显式受控路线。洛克通过已有来源 Join 指令进入持有名册，真实媒体经可信目录提供；私有探针地图和引用重新计算摘要，原发布包不改。

连续检查包括：三组编辑、空组和重复/未持有/disabled/失效请求拒绝，洛克和蒂娜参战、战后资源和一次奖励，三次存读档、切换两名士兵的另一组、跨图后再战。后备成员的完整资源、装备与能力逐字段保留。来源加入和重入验证不把菜单编辑当作取得角色。

受控界面检查保留原排序回归，并验证三组浏览、显式激活、成员换入换出、旧完整基线、I/O 与后台门控、媒体失败回滚及旧 owner 拒绝。声明的合成媒体用于合成正例，不证明浏览器图像解码或来源媒体身份。

本次统一验证通过：TypeScript 2796/2796、Python 工具43/43与来源绑定16/16；46条共同检查包含45条受控系统合同和1条仍未完成的来源路线检查。新编队连续流程9/9、编队受控界面16/16，原有22份发布包文件保持逐字节不变。具体结果见忽略的 `build/reports/v70-validation-summary.json`。受控系统合同、来源剧情准入和全游戏验收仍是独立范围。

## 保留的核心缺口

保存组选择未恢复来源多队地图的独立位置、控制与切换；`CanPartySwitching` 的原门禁保留。完整来源 UI 的场所和剧情许可也需独立恢复。

魔石有27个来源内容与92条类型2学习记录，但装备消费者、召唤和成长奖励字典尚未闭合。当前非零魔石装备及相关成长仍阻塞，不能用菜单展示或清空校验代替完整实现。后续补字段魔法和魔石的取得、装备、学习、战斗及保存合同，再沿内容依赖批量推进。
